## 推荐执行方案

### 1. 冻结本地基准

以当前 Git 提交 `e0ff270 图12复现问题的出现` 为基准，不改动原项目，生成一个明确的云端副本。

副本包含：

- 主程序 `.py`
- `notebooks/`
- `PLAN.md`、精读笔记和 `monte_numerical.md`
- Fig.12 原图锚点及当前试算结果
- Colab 依赖清单
- Git 提交号、文件清单与校验值
- 当前默认配置和随机种子

默认排除：

- `.git`
- Python 缓存
- 临时解压目录
- 可重新生成的大体积中间文件
- 与计算无关的重复 PDF

排除内容会写入 manifest，不会静默遗漏。

### 4. 先做云端一致性验收

不会直接跑大样本。先在相同初态、随机种子和配置下比较本地与 Colab：

- 时间网格及红移网格；
- 各壳层的 \(\rho\)、\(v\)、\(a_h\)；
- `N_sample`、`N_hard`、`N_merged`、`N_invalid`；
- 固定样本的最终 \(a,e\)；
- R1、R5 的完整演化与 GW-only 对照；
- 小样本运行时间和内存峰值。

只有结果一致或差异获得解释后，才开展新方案。

### 5. 云端研究方案分支

建议将每种方案做成独立配置，而不是覆盖主程序：

- `baseline_prada_strict_euler`：当前 Prada12-HMF、严格联合抽样、2 Myr Euler 基准；
- `euler_convergence`：固定初态扫描局部步长；
- `adaptive_integrator`：带 \(a=0\)、\(e=0/1\) 事件检测的自适应积分；
- `gw_only_control`：关闭环境项；
- `sampling_paper_order_diagnostic`：论文文字顺序抽样，仅作复现诊断；
- `k_endpoint_sensitivity`：检查 \(e>0.9\) 时不同 \(K\) 处理；
- `environment_convention`：逐项改变浓度、速度评价半径或 \(\mu\)；
- `scheme_b_cohort`：等方案 A 的数值问题解决后，再研究 cohort 继承。

严格联合抽样与论文顺序诊断会始终分开，避免混成一个“修正版”。

### 6. 算力策略

当前代码主要是 NumPy CPU 向量化，选择 GPU 并不会自动加速。推荐顺序是：

1. Colab CPU 做一致性和步长收敛；
2. 使用分块、并行壳层或时间片提高 CPU 利用率；
3. 只有运行时间仍不可接受时，再建立单独的 CuPy/JAX GPU 分支；
4. 每个时间片或壳层保存检查点，运行时中断后可以续跑；
5. 最终大规模 \(2\times10^6\) 样本计算根据实测吞吐量决定是否使用付费 Colab或其他持久云主机。

需要注意：Colab 运行时会重置、硬件可用性会变化，而且 Drive 挂载通常需要用户授权；因此它适合交互式实验和分块 Monte Carlo，不适合没有检查点的长时间无人值守任务。[Colab 官方资源限制说明](https://research.google.com/colaboratory/faq.html)
